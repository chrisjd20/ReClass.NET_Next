# Focused debugger validation

Run this batch only at the two consolidated checkpoints in roadmap section 13. Building these fixtures does not establish Windows or Linux runtime acceptance.

`build-target.sh` builds the same explicit x64 instruction sites for Linux and Windows with the pinned Linux NASM built by Docker. Outputs are `/out/validation/linux/debugger-target` and `/out/validation/windows/debugger-target.exe`. The fixture accepts `modify`, `hook`, `thread`, `stop`, `reset`, `values`, and `exit` on standard input. It prints its process ID, both object addresses, instruction entry addresses, and the RIP-relative bias address. Linux's fixture opts into sibling ptrace access for its own process.

Linux also requires `debugger-launcher` beside `debugger-target`. The launcher forks the fixture and inherits its standard streams, keeping Mono's registered child separate from the ptrace debuggee. The walkthrough opens the fixture PID printed in its identity line. It observes stdout EOF and native exit events without managed `HasExited`, `ExitCode`, or `WaitForExit` polling while attached.

Build `FocusedChecks.csproj` with `AppOutputPath=/out/app` and copy packaged `Tools/nasm` or `Tools/nasm.exe` beside its output under `Tools/`. The standalone console batch uses five grouped checks: conversion/boundaries; coordinated transactions and simulated partial-write recovery; near/far hook layouts, RIP-relative relocation, semantic insertion and retirement; shared operand addresses and condition limits; and inactive XML persistence plus bounded unique pattern resolution. It uses a managed fake target to provoke errors that are unsuitable for routine runtime walkthroughs. It never substitutes for the native walkthrough.

After fixing a failure, select only the failed and remaining focused groups, for example `FocusedChecks.exe hooks conditions persistence`. Group names are `conversion`, `transactions`, `hooks`, `conditions`, and `persistence`; omitting them runs all five. The real walkthrough supports `--from=N` to begin at group 1 through 5 and run that group plus the remaining groups on a fresh controlled target. For example, `RuntimeWalkthrough.exe --from=3 <fixture-path>` reruns hooks, inspection, and lifecycle without repeating successful conversion or editing scenarios.

For each platform's controlled target walkthrough:

1. Start the target and attach ReClass to its printed process ID. Scan/follow `object1`, find writes, and send `modify`. Confirm the instruction row identifies the stable `fixture_modify` entry and distinguishes both object addresses. Edit the two-byte `dec` into `inc`, preview, apply, and send `modify` again. Confirm both values increase. Restore and confirm the next command decreases them. Preview a shorter NOP edit and reject a stale or overlapping edit.
2. Use the first two NOPs of `fixture_hook` as the selection. Prepare a replacement longer than two bytes. Verify the preview separates selected NOPs from the displaced RIP-relative load, identifies the jump and return, and assembles at the allocation origin. Apply, send `hook`, restore, and confirm the retained allocation remains reported as retired. Use the fixture's later `test/jz` sequence for a reviewed direct-branch relocation case.
3. Add an instruction access watch at `fixture_modify`, send `modify`, and follow both reported object addresses. Filter one object with a Before condition. Pause and collect a short bounded trace, stop, and export it. Send `thread` and `stop` to check new-thread installation and cleanup.
4. Save definitions, restore/detach, restart the target, and reopen the project. Confirm definitions remain inactive, explicitly resolve a module offset or unique pattern, and reject a mismatched identity or ambiguous pattern. Send `exit` while attached to check transient-state invalidation.

Record the actual package identity, OS/runtime identity, the first useful failure, and which steps passed or remain pending. Windows acceptance requires an actual Windows process; a Linux build or PE inspection cannot provide that result.

The Docker `debugger-validation-export` stage exports an isolated checkpoint bundle to `dist/debugger-validation/`. After building/exporting it once, the focused console is `focused/FocusedChecks.exe`. The real-provider walkthrough is `focused/RuntimeWalkthrough.exe`, with `targets/linux/debugger-target` or `targets/windows/debugger-target.exe` as its first argument. For example, from the bundle root run `mono focused/RuntimeWalkthrough.exe targets/linux/debugger-target` on Linux, or `focused\RuntimeWalkthrough.exe targets\windows\debugger-target.exe` on Windows. An optional second argument chooses the bounded trace CSV output path. The walkthrough creates its own target processes and reports each scenario's actual result; it uses no fake provider. It directly exercises the shared services, so the UI launch/follow workflow still requires its brief platform confirmation.

For the final brief Windows package confirmation, copy only `RuntimeWalkthrough.exe` and its generated `.exe.config` if present into the extracted final application directory, leaving the package's application assembly, native core, and bundled NASM in place. Run `RuntimeWalkthrough.exe --smoke <path-to-debugger-target.exe>`. This resolves the actual package files beside the harness, prints the loaded application path, checks conversion, applies the increment and verifies both objects, restores exact original bytes, confirms decrement behavior, and detaches. The smoke option does not run the full five-group walkthrough. The same option also works under Mono with the Linux fixture when a focused confirmation is warranted.
